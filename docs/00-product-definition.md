# 产品定义

## 一句话

AtlasForge 是一个本地优先的 AI 工程运营工作台：它扫描你的本机项目和远端仓库，建立知识索引和健康画像，然后让 AI 在可审计、可回滚、可验证的边界内完成维护、修复、发布和知识沉淀。

## 用户画像

核心用户是高频使用 AI 编程工具的人，尤其是同时拥有多个本地项目、GitHub 仓库、实验目录、发布物、文档和自动化脚本的人。

这类用户的问题不是“不会写代码”，而是：

- 项目太多，状态不可见。
- 仓库长期散落在不同目录，哪些能发布、哪些有风险不清楚。
- AI 能一次性修一个问题，但缺少跨仓库、跨会话的长期记忆和治理。
- 发布、CI、README、依赖、安全、测试这些工程卫生工作反复出现，适合 AI 做，但需要约束。
- 本机文件、聊天记录、仓库经验和历史坑点没有变成可查询资产。

## 北极星目标

让用户可以说一句“把我这些项目整理成可维护、可发布、可展示的状态”，AtlasForge 能持续拆解、执行、验证、复盘，并把结果沉淀到知识库。

## 产品能力层

### L1：资产地图

目标：知道“我有什么”。

能力：

- 扫描配置的本机根目录，发现 Git 仓库、普通项目、文档目录、构建产物。
- 识别语言、框架、包管理器、测试脚本、CI、远端仓库、发布方式。
- 展示仓库状态：dirty worktree、未推送提交、默认分支、最近活动、大小、风险标签。
- 建立资产关系：本机目录到 GitHub repo、repo 到 release、repo 到 Pages/网站、repo 到文档。

### L2：知识索引

目标：知道“每个项目是什么、为什么这样做、怎么维护”。

能力：

- 文件名、全文、代码符号、README、配置、提交记录、issue/PR 摘要索引。
- 语义搜索和关键词搜索混合召回。
- 自动生成项目卡片：定位、技术栈、运行命令、测试命令、发布命令、注意事项。
- 把审查结论、修复记录、CI 结果和 release 经验写回项目知识。

### L3：仓库体检

目标：知道“哪里坏、哪里弱、哪里值得修”。

能力：

- 多维健康评分：可运行性、测试、CI、依赖、安全、文档、发布、公开面、隐私、平台兼容。
- 检查 GitHub Actions 权限、action pin、Dependabot、release workflow、版本一致性。
- 检查 README、license、screenshots、demo URL、安装说明、贡献说明。
- 检查 secrets 泄漏风险、内部文档外露、构建产物误入仓库。
- 生成可执行修复计划，而不是泛泛建议。

### L4：AI 执行台

目标：把“建议”变成“完成”。

能力：

- 用户用自然语言创建任务，例如“把这个 repo 做成公开第一版”。
- AI 自动拆分：读取上下文、列风险、生成计划、申请权限、应用补丁、运行验证。
- 每个任务都有事件流、文件引用、命令记录、diff、测试结果、失败原因。
- 支持暂停、恢复、重试、回滚、交接给另一个 AI。

### L5：自动维护

目标：让重复工程工作自动发生，但不失控。

能力：

- 定期扫描项目状态。
- 自动开低风险 PR，例如文档链接修复、依赖小版本、CI pin 刷新。
- 对高风险任务只生成计划和 dry-run，等待用户确认。
- 观察 GitHub CI、release、Pages，失败时生成诊断任务。

### L6：个人工程记忆

目标：把每次维护变成未来 AI 的上下文。

能力：

- 自动总结每次任务的关键事实、命令、错误、修复策略、验证证据。
- 形成项目手册、发布手册、故障手册和偏好规则。
- 新任务开始前自动检索相关历史，而不是从零猜。

## 成功标准

AtlasForge 的成功不是页面好看，而是它能长期减少这些问题：

- “这个项目现在还能跑吗？”
- “这个仓库能不能公开？”
- “上次 release 是怎么做的？”
- “哪个 repo 有未提交改动？”
- “CI 为什么挂？”
- “哪些依赖或 workflow 已经过时？”
- “我应该让 AI 先修哪个项目？”

## 关键产品约束

- 必须本地优先，不能默认云端存储所有项目内容。
- 必须支持 Windows 作为一等环境。
- 必须允许用户配置哪些目录能读、哪些目录能写、哪些目录永远忽略。
- 必须对 Git 写操作、删除文件、发布、force push、release、凭据访问做高风险标记。
- 必须保存任务证据，否则自动化不可信。
